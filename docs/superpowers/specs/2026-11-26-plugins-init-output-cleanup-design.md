# `groot plugins init` 输出精简设计文档

## 一、功能设计

### 1.1 功能概述

`groot plugins init` 负责创建 `{GROOT_HOME}/plugins/` 的固定目录布局、所有插件共用的虚拟环境 `plugins/.venv`，并在该环境中安装基础依赖。命令的输出只陈述它实际完成的动作及其结果，供使用者核对每一步是否成功、下一步该做什么。

插件业务依赖（各插件自己 `requirements.txt` 中声明的包）不在该命令的处理范围内：它们所在的插件目录不由本命令创建，哪些插件存在也随使用者的选择而变。这类依赖的安装方法由用户手册说明，命令本身不输出相关命令。

### 1.2 输出内容

命令按执行顺序输出以下内容：

| 阶段 | 输出 |
|------|------|
| 开始 | `初始化插件环境...` 与空行 |
| 工作目录 | 新建时打印创建成功；已存在时不打印 |
| 目录布局 | 全部已存在时打印跳过说明；否则逐项打印本次新建的路径 |
| 共享虚拟环境 | 新建时打印创建成功（路径按主目录缩写为 `~`）；已存在时打印跳过说明 |
| 基础依赖 | 开始提示、结果（`基础依赖安装完成` 或失败说明） |
| 解释器 | `解释器: <路径> (<版本>)`，版本未知时省略括号部分 |
| 收尾 | `初始化完成`；基础依赖安装失败时为 `初始化完成（基础依赖需手动安装）` |

基础依赖安装失败时，失败分支额外输出 pip 输出末尾、补装基础依赖的手动命令（含离线 wheel 用法）以及缺 pip 时的系统包安装提示。

插件业务依赖的安装方法与可选路径由用户手册描述（README §6.4、§6.5、§7.8）：可在 `groot plugins` 进入的已激活 shell 中用相对路径安装，也可直接调用共享虚拟环境的 pip 用绝对路径安装。

### 1.3 设计细节

- **输出面**：命令的所有输出经 `PluginsInitOptions.Out` 注入，便于测试断言完整输出。
- **删除的提示**：原先在打印解释器之后无条件输出的一行
  `<venv>/bin/pip install -r <plugins>/<插件名>/requirements.txt` 不再输出。该行带字面占位符 `<插件名>`，在插件目录尚未就位时无法执行，且在成功与失败两条路径上都出现，容易被误读为失败提示或待执行动作。
- **保留的内容**：基础依赖失败分支的手动安装命令保留，它对应命令未完成的工作，属于结果说明的一部分。
- **代码清理**：`internal/cmd/plugins.go` 中该行删除后不再使用 `path` 包，同步移除导入；`internal/cmd/plugins_test.go` 中的对应断言、`subPluginRequirements` 变量与 `path` 导入同步移除。
- **测试**：`TestRunPluginsInit_DepsFailureWritesManualCommands` 继续校验基础依赖失败分支的完整手动指引，去掉插件提示断言；新增断言确认输出中不再出现 `<插件名>`，防止提示回潮。
- **文档同步**：更新 `docs/superpowers/specs/2026-11-24-python-plugins-init-command-design.md` 的执行流程第 6 步与迭代说明；README 现有描述（§6.4 的失败提示说明、§6.5/§7.8 的安装方法）与本设计一致，无需改动。

## 二、迭代说明

### 2.1 与上一版差异

- 移除：`groot plugins init` 在打印解释器信息后输出的插件业务依赖安装提示行（含 `<插件名>` 占位符与完整绝对路径）。
- 移除：因此不再使用的 `path` 包导入（`internal/cmd/plugins.go`、`internal/cmd/plugins_test.go`）与测试断言。
- 保留：基础依赖安装失败时的手动安装命令、pip 输出末尾与缺 pip 提示，输出行为不变。
- 调整：设计文档 `2026-11-24-python-plugins-init-command-design.md` 的执行流程第 6 步改为只包含基础依赖失败时的手动命令与收尾状态行，并补充本迭代说明。

### 2.2 方案选择

- **方案 A（选定）：移除该提示。** 信息已由 README 完整覆盖（交互 shell 与绝对路径两种方式），且提示在多数场景下当下不可执行；移除后成功路径的输出只包含已完成的事项，语义单一。
- 方案 B：保留提示但加引导语并改为相对路径（`.venv/bin/pip install -r <插件名>/requirements.txt`）。降低了误读风险，但仍在 init 阶段给出一个通常无法立即执行的命令，并与 README 中的两种方式重复表述。
- 方案 C：仅当 `plugins/` 下检测到有效插件时才打印各自的安装命令。提示变得可执行，但 init 承担了插件发现与依赖检查的职责，输出随环境变化，且与 `install --help`、README 的既有分工重叠，收益不足以抵消复杂度。
