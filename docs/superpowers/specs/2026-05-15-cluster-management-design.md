# Groot 单机多实例集群管理设计

## 概述

Groot 当前是单实例架构，所有状态（session、schedule、memory）存储在 `GROOT_HOME` 目录下。多实例共享同一 `GROOT_HOME` 后，数据层天然共享，但需要在多个实例间选出一个 Leader 来执行全局唯一任务（清理 session、同步调度、运行用户定时任务等），避免多实例重复执行。

本设计基于**文件系统**实现 Leader 选举、成员发现、心跳存活检测和故障转移，不引入任何外部依赖。

## 设计目标

- 同一台机器上运行多个 Groot 实例，共享 `GROOT_HOME`
- 自动选举 Leader，Leader 负责执行全局唯一任务
- Leader 宕机后自动故障转移
- 不新增配置项，默认走集群模式（单实例时自己是天然 Leader）
- 对现有代码侵入最小

---

## 一、核心概念

### 注册编号

每个实例在注册时生成一个**注册编号**，即注册时刻的时间戳，精确到毫秒，格式 `YYYYMMDDHHMMSSmmm`。示例：`20260515143022123`。

注册编号是实例在集群中的**唯一标识**，保存在内存中，用于：

- 选举排序：注册编号按字符串比较，**最小的当选 Leader**
- 文件定位：心跳时通过注册编号找到自己的注册文件

注册编号在以下时机会更新：
- 实例首次启动注册时生成
- 心跳中发现自己的注册文件丢失，重新注册时生成新的注册编号

其余时间（正常心跳）注册编号保持不变。

### 注册文件

注册文件是实例在磁盘上的存在凭证，存放于：

```
{GROOT_HOME}/cluster/members/{注册编号}
```

**文件内容**：

```
{role}|{host}:{port}|{pid}
```

| 字段 | 说明 |
|------|------|
| `role` | `leader` 或 `follower` |
| `host:port` | 实例的 HTTP 监听地址 |
| `pid` | 操作系统进程号 |

示例：
```
leader|192.168.1.10:8080|12345
follower|192.168.1.10:8081|12346
```

### 注册编号与注册文件的关系

- 注册编号是注册文件的**文件名**（不含路径）
- 注册文件是注册编号在磁盘上的**物理载体**
- 实例内存中始终保存自己的注册编号，心跳时用它定位对应的注册文件
- 心跳只覆盖写入注册文件的内容，**不改变文件名（即不改变注册编号）**

### 心跳与存活判断

- 心跳周期：**每 3 秒**一次
- 心跳动作：写入注册文件内容，系统自动更新文件的修改时间（mtime）
- 存活判断：`当前时间 - 注册文件 mtime > 7 秒` → 实例视为宕机

## 二、注册流程

每个实例在以下场景触发注册流程：

- **首次启动**：进程启动，集群目录中尚无自己的注册文件
- **重新注册**：心跳中发现自己的注册文件丢失（被 Leader 清理或意外删除）

注册流程步骤：

1. 确保 `{GROOT_HOME}/cluster/members/` 目录存在
2. 生成**新注册编号**（当前时刻时间戳）
3. 扫描目录中所有注册文件，过滤存活实例（注册文件 mtime < 7s）
4. 确定角色：
   - 无存活实例 → **leader**
   - 有存活实例 → 按注册编号排序，自己的注册编号最小 → **leader**，否则 → **follower**
5. 以新注册编号为文件名创建注册文件，写入 `{role}|host:port|pid`
6. 将新注册编号保存到内存
7. 角色为 leader → 启动全局任务（scheduler）；follower → 不启动

### 设计要点

注册编号在每次注册时**重新生成**。这意味着：
- 崩溃恢复的实例，旧注册文件已被 Leader 清理，重新注册时生成**新的、更大的注册编号**，自然排在存活实例之后，结果为 follower——无需任何特殊判断。

---

## 三、心跳流程

每隔 3 秒，每个实例根据自己的当前角色执行对应的心跳逻辑。心跳的起点都是**检查自己的注册文件是否还在**。

### Leader 心跳

1. 以注册编号为文件名，检查自己的注册文件是否还在
   - **在** → 覆盖写入 `leader|host:port|pid`（更新 mtime），继续执行步骤 2
   - **不在** → 停止全局任务，走注册流程重新注册，本轮结束
2. 扫描 `cluster/members/` 目录，清理所有超时的注册文件（mtime > 7s）

### Follower 心跳

1. 以注册编号为文件名，检查自己的注册文件是否还在
   - **在** → 继续执行步骤 2
   - **不在** → 走注册流程重新注册，本轮结束
2. 扫描 `cluster/members/` 目录，过滤存活实例（注册文件 mtime < 7s），按注册编号排序
3. 自己的注册编号最小 → 覆盖写入 `leader|host:port|pid`，身份转为 leader，清理所有超时注册文件，启动全局任务
   自己不是最小 → 覆盖写入 `follower|host:port|pid`

### 设计要点

- **只有 Leader 负责清理超时的注册文件**，follower 不删除任何文件
- 文件丢失时，leader 和 follower 都走同一套注册流程重新注册

---

## 四、全局任务

只有 Leader 负责执行全局唯一任务，通过 gocron 调度器管理：

| 任务 | 来源 | 周期 |
|------|------|------|
| Memory cleanup | `memory.NewCleanupTask` | 每天（配置时间） |
| Schedule sync | `schedule.NewSyncTask` | 30 秒 |
| 用户定时任务 | `schedule.Engine` 加载 | 按 cron 定义 |

### 角色切换时的启停

- 升为 leader → 创建新的 gocron 实例，注册全局任务，Start()
- 降为 follower → Shutdown() 当前 gocron 实例

---

## 五、故障转移

### Leader 宕机

1. Leader 进程崩溃，其注册文件 mtime 停止更新
2. 各 follower 心跳时扫描目录，过滤存活实例（mtime < 7s），原 leader 的注册文件因超时被自然排除
3. 存活实例中注册编号最小的 follower，发现自己就是最小 → 提升为 leader
4. 新 leader 清理所有超时的注册文件（可能包含原 leader 和其他超时 follower），启动全局任务

### Follower 宕机

1. Follower 进程崩溃，其注册文件 mtime 停止更新
2. 7 秒后，leader 心跳时发现该注册文件超时并清理
3. 不影响集群运行

### 进程被强杀（kill -9）

同 Leader/Follower 宕机，注册文件残留，由 Leader 在心跳中清理。

### 进程正常退出（SIGTERM/SIGINT）

1. 优雅关闭流程中删除自己的注册文件
2. 如果是 leader 退出：其注册文件被删除，各 follower 心跳过滤存活实例时自然排除之 → 注册编号最小者提升为 leader
3. 如果是 follower 退出：其注册文件被删除，leader 照常运行

---

## 六、边界场景

### 磁盘满 / 无写入权限

心跳写入失败 → 注册文件 mtime 不更新 → 7 秒后被 leader 视为超时并清理。被清理的实例发现注册文件不在 → 走注册流程重新注册，并持续告警日志。

### 同一毫秒启动

同一毫秒启动两个实例的操作场景不会发生，不做特殊处理。

## 七、模块结构

新增 `internal/cluster/` 包：

```
internal/cluster/
├── member.go       # 成员注册、心跳、发现
├── election.go     # 角色判定与选举逻辑
└── cluster.go      # 统一入口（Cluster 结构体，Join/Leave/SetCallbacks）
```

全局任务启停通过 `onBecomeLeader` / `onLoseLeader` 回调触发，无需单独文件。

### 依赖边界

- `cluster/` 只依赖 `logger/`，host、port、homeDir 等信息通过构造函数参数传入
- `cluster/` 不感知 memory、schedule、scheduler 的具体逻辑——通过回调函数交互
- `main.go` 是唯一将 cluster 与 scheduler 等组件粘合的地方

### 对现有代码改动

| 文件 | 改动 |
|------|------|
| `cmd/groot/main.go` | 启动/关闭流程插入 cluster 初始化和角色判定；scheduler 根据角色条件启动 |

---

## 八、配置

不新增 `config.yaml` 配置项。集群模式默认启用，无需用户配置。

心跳间隔（3 秒）和超时时间（7 秒）作为常量硬编码在 `internal/cluster/` 中。

---

## 九、测试策略

### 单元测试

- 选举逻辑：验证排序和角色判定
- 超时判断：验证 mtime 检测准确性
- 文件清理：验证 leader 正确清理超时文件

### 系统测试

- 单实例启动 → 自己是 leader
- 第 2 个实例启动 → follower
- 杀掉 leader → follower 提升为 leader
- 重启老 leader → 变为 follower
- 多实例同时运行 → 只有一个 leader
