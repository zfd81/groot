# 实例重启与进程监督设计文档

## 一、功能设计

### 1.1 功能概述

Groot 服务以「监督进程 + 工作进程」的双进程模型运行。使用者敲一条 `groot` 启动的是监督进程，它立即拉起一个工作进程来承担全部业务（加载配置、MCP、Skills、数据库、HTTP 服务、集群心跳等）。监督进程本身不加载任何业务资源，只负责三件事：拉起工作进程、按工作进程的退出码决定下一步、把外部的关闭请求转交给工作进程。

在此基础上，Groot 提供**实例重启**能力：管理员在 Web 界面 **设置 → 集群管理** 中对任意一个实例点击「重启」，目标实例的工作进程走完整的优雅关闭流程后以约定的退出码退出，监督进程随即拉起一个全新的工作进程。重启过程中该实例有数秒不可用，配置、MCP、子 Agent 定义等需要重启才能生效的变更在新工作进程中生效。

解决的问题：

- 修改 `config.yaml`、`mcp/`、`subagents/`、`agent.md` 后必须重启服务才能生效，管理员需要登录服务器手动操作。
- 工作进程因异常崩溃后无人拉起，服务中断直到人工介入。
- 单机多实例和数据库集群场景下，需要逐台登录才能重启指定实例。

### 1.2 能力清单

| 能力 | 说明 |
|---|---|
| 双进程运行 | `groot` 默认以监督进程启动，业务全部在工作进程中执行 |
| 优雅重启 | 工作进程按现有关闭流程退出（离开集群 → 停 HTTP → 停消息层 → 关 MCP → 关子 Agent），监督进程重新拉起 |
| 崩溃自愈 | 工作进程异常退出时监督进程按指数退避重新拉起，连续快速失败达到上限后放弃并报错退出 |
| Web 重启入口 | 集群管理面板每张实例卡片提供「重启」按钮，二次确认后触发 |
| 跨实例重启 | 通过集群消息把重启指令投递到目标实例，单机多实例（SQLite）与数据库集群（MySQL/PostgreSQL）统一处理 |
| 本机标识 | 集群列表标出当前为浏览器提供服务的实例；重启本机时前端等待恢复后引导重新登录 |
| 单进程模式 | `--single-process` 跳过监督进程直接运行业务，供调试和由容器运行时托管重启的场景使用；该模式下拒绝重启指令 |
| 状态可见 | `/web/health` 与 `groot status` 展示进程模式与工作进程 PID |

### 1.3 进程模型

#### 1.3.1 角色划分

```
终端 / systemd / 容器
        │
        ▼
┌─────────────────────┐   stdin 管道（仅用于关闭通知）   ┌──────────────────────────┐
│  监督进程 (groot)    │ ───────────────────────────────▶ │  工作进程 (groot, 同一二进制) │
│  不读配置、不连库     │ ◀─────────────────────────────── │  startServer 全部逻辑       │
│  循环拉起 / 观察退出码 │          退出码                  │  MCP / LLM / HTTP / 集群    │
└─────────────────────┘                                  └──────────────────────────┘
                                                                     │
                                                          MCP stdio 子进程若干
```

- 工作进程由监督进程用 `os.Executable()` 取得自身路径、原样传递命令行参数并附加环境变量 `GROOT_SUPERVISED=1` 拉起。工作进程据此环境变量识别自己的角色。
- 工作进程的 stdout / stderr 直接继承监督进程，日志输出行为与单进程时完全一致。
- 工作进程的 stdin 是监督进程持有的一根管道。监督进程从不向其中写数据，只在需要工作进程停下时关闭它。
- `init`、`status`、`tail`、`user` 子命令不经过监督进程，行为不变。

#### 1.3.2 角色判定

程序入口按以下顺序判定：

1. 有子命令 → 执行子命令，结束。
2. 环境变量 `GROOT_SUPERVISED=1` → 以**工作进程**身份运行 `startServer`，启用 stdin 关闭监听。
3. 命令行含 `--single-process` → 以**单进程**身份运行 `startServer`，不启用 stdin 监听。
4. 其他 → 以**监督进程**身份运行。

#### 1.3.3 退出码约定

工作进程用退出码告诉监督进程下一步动作。这是工作进程向监督进程传递信息的唯一通道，不使用额外的 IPC。

| 退出码 | 常量 | 含义 | 监督进程动作 |
|---|---|---|---|
| 0 | `ExitOK` | 正常结束（收到关闭信号或管道关闭） | 监督进程随之退出，退出码 0 |
| 3 | `ExitRestart` | 请求重启 | 立即重新拉起（最小间隔 1 秒） |
| 其他 | — | 异常（崩溃、启动失败、被强制杀死） | 按退避策略重新拉起 |

退出码 3 的选择依据：1 是通用错误，2 是 Go 运行时 panic 与 flag 解析失败的退出码，都不能复用。

#### 1.3.4 关闭通知协议（管道）

监督进程向工作进程传达的信息只有一句「请停下来」，各平台统一用关闭 stdin 管道实现，不做信号与管道两套实现。

- 工作进程启动后开一个 goroutine 阻塞读取 stdin 直到 EOF 或错误，读到即触发优雅关闭，原因记为 `supervisor_closed`。
- 监督进程收到 SIGINT / SIGTERM 时：置 `shuttingDown = true` → 关闭管道写端 → 最多等待 **35 秒**（工作进程自身 30 秒关闭超时加 5 秒余量）→ 仍未退出则 `Process.Kill()` → 等待回收 → 以工作进程的实际结果退出（正常 0，否则 1）。
- 管道协议的附带保障：监督进程无论以何种方式死亡（包括 SIGKILL），操作系统都会关闭管道，工作进程读到 EOF 后自行优雅退出，不会留下孤儿进程占着端口。
- 终端 Ctrl+C 会同时打到整个前台进程组，工作进程会同时收到信号和管道 EOF，两条路径在工作进程内汇合于同一个 `sync.Once`，关闭流程只执行一次。

#### 1.3.5 退避与放弃策略

| 参数 | 值 | 说明 |
|---|---|---|
| 快速失败窗口 | 60 秒 | 工作进程存活不足 60 秒即异常退出，计为一次快速失败 |
| 退避序列 | 1s, 2s, 4s, 8s, 16s, 30s, 30s… | 连续快速失败次数决定等待时长 |
| 放弃阈值 | 连续 10 次 | 达到后监督进程在 stderr 打印明确错误并以退出码 1 退出，交由外层（systemd / 容器 / 人）处置 |
| 计数重置 | 工作进程存活超过 60 秒 | 之后再崩溃视为新的一轮，从 1 秒重新开始 |
| 最小拉起间隔 | 1 秒 | 对退出码 3 同样生效，避免极端情况下的紧密循环 |

启动期失败（如端口被占用导致工作进程 `exit 1`）同样走此策略：端口稍后释放即可自愈，长期占用则在约 3 分钟后放弃并报错，不会静默空转。

#### 1.3.6 监督进程的输出

监督进程不加载日志配置，所有输出走 stderr，带固定前缀 `[groot-supervisor]`，只记录：拉起（含工作进程 PID）、退出（含退出码与存活时长）、退避等待、放弃、转发关闭。信息量刻意保持极小。

### 1.4 工作进程生命周期控制器

`internal/lifecycle` 包提供 `Controller`，把工作进程的所有停止来源收敛为一个出口。

#### 1.4.1 停止来源

| 来源 | 触发方式 | 停止原因 | 退出码 |
|---|---|---|---|
| 操作系统信号 | SIGINT / SIGTERM | `signal` | 0 |
| 监督进程关闭管道 | stdin EOF | `supervisor_closed` | 0 |
| 重启指令 | 集群消息处理器调用 `RequestRestart` | `restart` | 3 |

#### 1.4.2 行为约束

- **只接受第一个原因**。`Controller` 内部用 `sync.Once` 保证后到的请求被忽略，关闭流程不会重入。
- **关闭顺序**沿用现有流程：离开集群 → 停 HTTP 服务（30 秒超时）→ 停消息层 → 关闭 MCP 客户端 → 关闭子 Agent 注册表。
- **显式刷新后退出**。因为需要指定退出码，主函数在 HTTP 服务返回后显式执行日志 `Sync` 与数据库 `Close`，然后 `os.Exit(code)`；不依赖 `defer`。
- **单进程模式**下 `RequestRestart` 返回错误 `ErrRestartUnsupported`，进程保持运行。以退出码 3 退出对没有监督进程的实例等同于停机，必须拒绝。

### 1.5 重启指令链路

```
浏览器 ──POST /web/cluster/{reg_id}/restart──▶ 任一实例 A
                                                  │ 写入集群消息（点对点，target_instance = reg_id）
                                                  ▼
                                            cluster_messages 表
                                                  │ 目标实例 B 的心跳轮询（≤ 3 秒）
                                                  ▼
                                    B 的 lifecycle 消息处理器
                                                  │ 返回成功 → 消费记录落库 → 1 秒后 RequestRestart
                                                  ▼
                                    B 工作进程优雅关闭，exit 3
                                                  ▼
                                    B 监督进程拉起新工作进程（新 reg_id）
```

#### 1.5.1 Web 端点

`POST /web/cluster/:reg_id/restart`，位于需要登录会话的 `/web` 分组，受现有限流中间件保护。

| 情况 | 响应 |
|---|---|
| reg_id 不在成员表 | 404 `{"status":"error","code":"member_not_found"}` |
| 目标是本机且本机为单进程模式 | 409 `{"status":"error","code":"restart_unsupported"}` |
| 消息写入失败 | 500 |
| 成功 | 202 `{"status":"accepted","reg_id":"…","self":true/false}` |

`self` 表示目标就是处理这次请求的实例，前端据此决定后续交互。

无论目标是否为本机，统一通过集群消息投递，不为本机另开直接调用路径。理由：只有一条链路便于测试与排错，消费记录表天然成为重启操作的审计日志，最坏 3 秒的额外延迟对重启操作无关紧要。

`GET /web/cluster` 的响应增加 `self` 字段（当前实例的 reg_id），供前端标记「本机」。

#### 1.5.2 集群消息

| 字段 | 值 |
|---|---|
| Type | `restart` |
| TargetInstance | 目标 reg_id（点对点） |
| TargetModule | `lifecycle` |
| Payload | `{"reason":"web","requested_by":"<登录用户系统编号>"}` |
| Priority | 1 |
| ExpiresAt | 创建时间 + 2 分钟 |

#### 1.5.3 消息处理器

`lifecycle.ClusterHandler` 注册为模块 `lifecycle`，处理 `restart` 类型：

1. 消息 `CreatedAt` 早于本进程启动时间 → 记日志、返回成功，不执行。这是针对至少一次语义的防重放保护。
2. 单进程模式 → 返回 `ErrRestartUnsupported`，消费记录标为失败，进程保持运行。
3. 否则 → 立即返回成功，并在 **1 秒后**异步调用 `RequestRestart`。先返回再退出，确保消费记录在进程消失前写入数据库。

#### 1.5.4 防死循环的三层保障

重启是会终止进程的操作，必须确保一条指令只导致一次重启：

| 层 | 机制 | 覆盖场景 |
|---|---|---|
| 1 | 点对点投递到旧 reg_id；实例退出时删除注册行，新进程使用新 reg_id | 新进程根本查不到发给旧身份的消息 |
| 2 | 处理器先返回成功再延迟退出 | 消费记录在退出前落库，同一进程不会重复处理 |
| 3 | 忽略早于进程启动时间的消息 | 极端情况下消费记录写入失败时的兜底 |

第一版只发送点对点重启消息。广播重启（全部实例）不在本版范围：新 reg_id 没有广播消息的消费记录，会被重新投递，且第 3 层依赖发送方与接收方的时钟，跨主机存在时钟偏差风险。广播重启需要滚动策略与额外去重设计，另行立项。

### 1.6 前端交互

#### 1.6.1 集群管理面板

- 每张实例卡片右侧增加「重启」图标按钮；当前为浏览器服务的实例（`reg_id === self`）显示「本机」标签。
- 点击弹出确认框，文案说明：进行中的对话会被中断；该实例约有数秒不可用；若为本机，重启后需要重新登录。
- 确认后调用重启端点。收到 404 提示实例已不存在并刷新列表；收到 409 提示该实例以单进程模式运行不支持重启。

#### 1.6.2 重启中状态

实例重启后 reg_id 会变化，但地址（IP:PORT）不变，因此以地址为键跟踪「重启中」状态：

- 收到 202 后把该地址加入 `restarting` 集合，卡片显示「重启中」并禁用按钮。
- 面板现有的 5 秒轮询继续运行。当列表中出现同地址且 `created_at` 晚于点击时刻的成员时，移出集合，恢复正常显示。
- 60 秒内未恢复则移出集合并提示「实例未在预期时间内恢复，请检查其日志与运行模式」。远程单进程实例拒绝重启时即表现为此情况。

#### 1.6.3 重启本机

Web 登录会话保存在工作进程内存中，重启后必然失效。`self` 为 true 时：

1. 显示全屏遮罩「实例重启中，完成后将跳转登录页」。
2. 每秒请求 `/web/health`（免登录）。先等到至少一次失败或 10 秒过去（确认旧进程已退出），再等到连续两次成功（确认新进程就绪）。
3. 跳转登录页。
4. 90 秒内未恢复则关闭遮罩并提示失败。

### 1.7 状态可见性

`/web/health` 的 `environment` 检查项增加两个字段：

| 字段 | 说明 |
|---|---|
| `pid` | 工作进程 PID（与集群成员表中的 PID 一致） |
| `process_mode` | `supervised` 或 `single` |

`groot status` 相应增加「进程模式」与「PID」两行。集群成员表中登记的 PID 是工作进程 PID，即真正承担业务的进程。

### 1.8 命令行

```
groot                     # 默认：监督进程 + 工作进程
groot -p 9090             # 参数原样传给工作进程
groot --single-process    # 单进程运行，不支持重启，供调试或容器托管场景
```

`--single-process` 的适用场景：本地调试需要单一 PID；容器编排已配置 `restart: always` 且不需要 Web 重启入口。

### 1.9 稳定性分析

| 场景 | 行为 |
|---|---|
| 工作进程 panic | 退出码 2 → 监督进程按退避拉起；日志中有 panic 堆栈 |
| 工作进程启动即失败（端口占用、配置错误） | 退避重试，约 3 分钟后放弃并以退出码 1 报错，不静默空转 |
| 优雅关闭卡在 MCP 客户端 | 工作进程自身 30 秒超时；监督进程 35 秒后强制 Kill；被 Kill 视为异常退出，走退避拉起 |
| 监督进程被 SIGKILL | 管道关闭 → 工作进程优雅退出 → 端口释放，无孤儿进程 |
| 工作进程被 SIGKILL | 监督进程 `Wait` 返回 → 按异常退出拉起；MCP stdio 子进程失去父进程后随其 stdin 关闭而退出 |
| 终端 Ctrl+C | 两进程同时收到；工作进程内两条路径 `Once` 汇合；监督进程等待后退出，不再拉起 |
| systemd `stop` | 默认 `KillMode=control-group` 两进程同时收到 SIGTERM，行为同 Ctrl+C；若只发给主 PID，管道协议兜底 |
| 容器内 PID 1 | 监督进程作为 PID 1 注册了信号处理，SIGTERM 正常转发；工作进程是其直接子进程，`Wait` 正常回收 |
| 重启后端口未及时释放 | 新工作进程启动检查发现端口占用 → 退出 1 → 退避 1 秒后重试，自愈 |
| 同一实例连续收到两条重启指令 | 第二条在 `Once` 中被忽略；新进程收不到发给旧 reg_id 的消息 |
| 消费记录写入失败 | 消息在下一轮重新投递，但进程已退出；新进程因 reg_id 不同收不到 |
| 单进程模式实例收到重启指令 | 处理器返回错误，进程保持运行，消费记录标失败 |
| 多实例经负载均衡访问 Web | 浏览器请求可能落到任意实例，`self` 判断以处理请求的实例为准；内存会话跨实例不共享属既有约束 |

### 1.10 安全

- 重启端点位于登录会话保护的 `/web` 分组，与其他管理操作同等权限；API Key 不能调用。
- 端点只接受成员表中存在的 reg_id，不接受任意进程标识。
- 集群消息 Payload 记录发起用户的系统编号，消费记录表保留 30 天，可追溯谁在何时重启了哪个实例。
- 监督进程拉起工作进程时使用 `os.Executable()` 的绝对路径与原始参数，不拼接任何外部输入。

### 1.11 代码组织

```
cmd/groot/main.go                      角色判定；工作进程模式下接入 Controller，显式退出码
internal/lifecycle/
    role.go                            Role 枚举、DetectRole、ProcessMode、RestartSupported
    controller.go                      Controller：停止原因收敛、Once、退出码映射、单进程拒绝
    stdin_watch.go                     stdin EOF 监听
    supervisor.go                      监督进程主循环、管道、退避、信号转发
    cluster_handler.go                 集群消息处理器（模块 lifecycle）
    *_test.go
internal/api/handler/cluster.go        GET 增加 self；新增 Restart 端点
internal/api/router.go                 注册 POST /web/cluster/:reg_id/restart
internal/api/handler/health.go         environment 增加 pid / process_mode
internal/cmd/status.go                 输出进程模式与 PID
web/src/components/settings/ClusterPanel.vue   重启按钮、本机标签、重启中状态、本机重启流程
web/src/api/types.ts                   ClusterResp.self、RestartResp
web/src/i18n/messages/{zh-cn,en}.ts     文案
```

`internal/lifecycle` 不依赖 `internal/cluster` 以外的业务包；`cluster_handler.go` 只引用 `cluster.Message` 与 `cluster.MessageHandler` 接口。

### 1.12 测试策略

单元测试（Go）：

| 包 | 用例 |
|---|---|
| lifecycle/controller | 首个原因生效、后续忽略；三种原因到退出码的映射；单进程模式 `RequestRestart` 返回错误 |
| lifecycle/stdin_watch | 用 `os.Pipe` 模拟：关闭写端后回调触发；未关闭时不触发 |
| lifecycle/supervisor | 用测试二进制自举（`TestHelperProcess` 模式）：子进程 exit 3 被重新拉起；exit 0 后监督循环结束；连续快速失败触发退避并在阈值后放弃；关闭管道后子进程在超时内退出；超时后被强制 Kill |
| lifecycle/cluster_handler | 早于启动时间的消息被忽略；正常消息延迟后触发重启；单进程模式返回错误；重复消息只触发一次 |
| api/handler/cluster | 未知 reg_id 返回 404；本机单进程返回 409；成功返回 202 且消息字段正确；`self` 判断正确；GET 响应含 self |
| api/handler/health | environment 含 pid 与 process_mode |

## 二、迭代说明

### 2.1 与上一版差异

上一版 Groot 以单进程运行 `startServer`，没有重启能力。本版：

- 新增：`internal/lifecycle` 包，含监督进程、生命周期控制器、stdin 关闭监听、集群消息处理器。
- 新增：`groot` 默认启动方式改为监督进程拉起工作进程；新增 `--single-process` 标志保留单进程运行。
- 新增：环境变量 `GROOT_SUPERVISED=1` 作为工作进程的内部角色标记（由监督进程设置，使用者无需关心）。
- 新增：`POST /web/cluster/:reg_id/restart` 端点；`GET /web/cluster` 响应增加 `self` 字段。
- 新增：集群消息处理器模块 `lifecycle`，落实集群消息设计文档（2026-09-18）4.3 节预留的 `restart` 消息类型；`TargetModule` 由该文档示例中的 `restart` 定为 `lifecycle`，为后续 `shutdown`、`reload` 等同类指令预留同一模块。
- 新增：集群管理面板的重启按钮、本机标签、重启中状态、本机重启后引导重新登录。
- 调整：`/web/health` 的 `environment` 检查项增加 `pid`、`process_mode`；`groot status` 相应增加两行输出。
- 调整：工作进程退出改为显式 `os.Exit(code)`，日志刷新与数据库关闭在退出前显式执行。
- 修正：README 中「集群管理在 SQLite 单机模式下为空」的描述与实际行为不符（集群注册不区分数据库类型，单机多实例同样登记），随本版一并修正。
- 对齐：实施计划（`docs/superpowers/plans/2026-09-22-instance-restart.md`）把 Payload 的 `requested_by` 定为登录用户系统编号而非用户名，避免 ClusterHandler 增加 UserRepo 依赖；`NewServer` 增加 `clusterInst`、`role` 两个参数。
- 加固：工作进程按信号计数，第二次收到 SIGINT/SIGTERM 时立即以退出码 1 退出（避免优雅关闭卡住时无法中断）；`api.Server.Start()` 把启动期 panic 转为错误返回（避免工作进程以退出码 0 结束导致监督进程停止看护）。

### 2.2 明确不做的事项

- 广播重启（重启全部实例）：需要滚动策略与跨 reg_id 的去重，另行设计。
- 零停机重启（监督进程持有监听套接字传递给工作进程）：Windows 不支持 fd 传递，且几秒停机可接受。
- 脱离终端的后台守护（`groot start -d`）：与本功能正交，另行设计。
- Web 登录会话跨重启保持：会话存储改造属独立课题。
